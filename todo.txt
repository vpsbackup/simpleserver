Totp 远程备份：新增 JSON 上传接口
==================================

背景
----
Totp（/Users/dilfish/totp）要加「手动加密备份」：客户端把已加密的 store.json
POST 上来，需要立刻拿到服务器实际保存的文件名（用于列表、恢复、删除）。
现有 POST /upload 对非 curl UA 返回 HTML、对 curl UA 返回一行 URL，客户端没法
稳定解析，所以要一个返回 JSON 的新接口。

接口
----
POST /api/files/upload

- 鉴权：和 /api/files/list、/api/files/delete 相同（站点密码，X-Site-Token 或
  Authorization: Bearer）。POST 默认需要鉴权，needsAuth 不用改。
- 注册：在 api.go 的 switch 里加
      case "files/upload":
          if r.Method == http.MethodPost {
              ApiFilesUpload(w, r)
              return
          }
- 请求：multipart/form-data，单个 part，字段名 file（和 /upload 一致）。
  客户端文件名建议 store.<yyyyMMdd>.<HHmm>.totp；服务端和现在一样只保留扩展名，
  主体名仍是 RandStr(5)，不覆盖、不重名。
- 成功：200，Content-Type: application/json; charset=utf-8
      {"ok":true,"name":"Ab3dE.totp","url":"https://<domain>/dl/Ab3dE.totp","size":3120}
  name 必须是磁盘上的真实文件名（带扩展名），客户端靠它下载和删除。
- 这个接口总是回 JSON，不需要 Accept 协商（客户端带 Accept: application/json 可以忽略）；
  直接复用 msg.go 里的 writeJson。
- 失败：沿用 /upload 的文案与状态码，http.Error 纯文本即可
      405  bad method for file upload
      400  bad upload request        （不是合法 multipart）
      400  no file part              （没有 file part）
      413  upload quota exceeded
      413  file exceeds per-file size limit
      500  upload failed

实现（复用现有代码，不复制一份）
--------------------------------
- 把 upload_lib.go 里 UploaderService.Handler 中「遍历 multipart、把 file part
  交给 WriteFile」的那段抽成内部方法，例如
      func (u *UploaderService) writeMultipartFile(r *http.Request) (written int64, name string, err error)
  Handler 和新接口都调用它；WriteFile、配额预留、失败清理都不动。
- 内部方法用 sentinel error 返回「bad multipart / no file part」，再用一个共享的
  uploadErrorToHTTP(w, err) 映射状态码，保证 /upload 现有响应逐字不变。
- ApiFilesUpload 只做三件事：方法检查 → writeMultipartFile → writeJson。
- 不需要新存储、新配置、新配额；单文件上限、总配额、失败清理沿用现有逻辑。
- 响应不需要 md5（不要在写盘路径上额外算一遍）。

测试（按现有 *_test.go 风格）
-----------------------------
- 成功：200 + JSON 里 name/url/size 正确，且磁盘上真的存在该文件；
- 方法不是 POST → 405；
- 不是 multipart / 没有 file part → 400；
- 配额或单文件超限 → 413；
- 配置了站点密码时无 token → 401，带 X-Site-Token → 200；
- 现有 /upload、/api/files/list、/api/files/delete 的测试保持通过。

客户端约定（totp 侧，见 totp/DESIGN.md §8）
------------------------------------------
- 备份：POST /api/files/upload，header X-Site-Token: <站点密码>，
  multipart 文件名 store.<yyyyMMdd>.<HHmm>.totp，body 是加密后的 store.json；
  成功后用返回的 name 更新「最新备份」。
- 列表：GET /api/files/list，只保留 name 以 .totp 结尾的，modtime 倒序。
- 恢复：GET /dl/<name> → importCompatibleStore（增量、同名整份拒绝）。
- 删除：POST /api/files/delete {"name": ...}。
- 站点密码不落日志；备份只手动触发，没有后台同步。

实现记录（已完成）
==================

改动文件
--------
- api.go：注册 `case "files/upload"`，**无条件**委派给 ApiFilesUpload（理由见下）。
- upload_lib.go：抽出 `(*UploaderService).writeMultipartFile`，新增两个 sentinel
  error 和共享的 `uploadErrorToHTTP`；Handler 瘦身，其余逻辑不动。
- upload.go：新增 ApiFilesUpload（log → 方法检查 → writeMultipartFile → writeJson）。
- upload_api_test.go（新增）：6 个测试。

核心函数
--------
    func (u *UploaderService) writeMultipartFile(r *http.Request) (written int64, name string, err error)
    func uploadErrorToHTTP(w http.ResponseWriter, err error)

- writeMultipartFile 返回的错误集合：errUploadBadMultipart / errUploadNoFilePart /
  WriteFile 原样透传的 errUploadQuota、errUploadTooLarge 及其它写盘错误。
- uploadErrorToHTTP 映射：quota→413 "upload quota exceeded"，
  too large→413 "file exceeds per-file size limit"，
  bad multipart→400 "bad upload request"，no file→400 "no file part"，
  其它→500 "upload failed"。文案与状态码与改动前逐字一致。
- ApiFilesUpload 只有三件事：方法检查（非 POST→405 "bad method for file upload"）
  → writeMultipartFile → writeJson{ok,name,url,size}。url = u.BaseURL + name，
  size 和 name 都是 WriteFile 的真实返回值；不额外算 md5。

与上面「接口」一节的偏差
----------------------
1. 路由改为无条件委派：

       case "files/upload":
           ApiFilesUpload(w, r)
           return

   原文只在 POST 时才调用，这会让 ApiFilesUpload 里的 405 分支永远不可达，
   非 POST 请求落到 api.go 末尾返回 200 "bad api request name"，与「方法不是
   POST → 405」冲突。方法检查统一放在 handler 里。

2. 抽方法时必须保留的语义（否则 /upload 响应会变）：
   - part 读取失败时，若已经存下了文件（savedName != ""），仍然算成功（break），
     不能返回错误；
   - 只落第一个 file part，其余 part 一律 Close() 排空，保证请求体被消费；
   - part.FormName() == "file" && part.FileName() != "" 两个条件都保留。

按要求本次不做
--------------
- 不加 O_EXCL 重试（低频备份，5 字符随机名碰撞可忽略，WriteFile 仍是 os.Create）；
- 不做幂等、不做自动清理、不动单文件上限/总配额；
- /dl/<name> 仍是公开路径，安全性依赖客户端加密 + 文件名熵，已知并接受。

测试（upload_api_test.go）
--------------------------
- TestApiFilesUploadReturnsRealName：200 + JSON（ok/name/url/size）+ 磁盘文件
  内容 + name 为 RandStr(5)+".totp" + 客户端文件名未被采用 + 配额账目一致。
- TestApiFilesUploadBadMethodThroughApiHandler：GET/PUT/DELETE 走 ApiHandler → 405。
- TestApiFilesUploadBadRequest：非 multipart → 400 bad upload request；
  无 file part → 400 no file part；且无残留文件。
- TestApiFilesUploadLimits：单文件超限、总配额超限 → 413，各自文案正确，无残留。
- TestApiFilesUploadNeedsAuth：走真实 InitMux，无 token → 401，
  带 X-Site-Token → 200 且 url 使用 Cfg.Domain，文件落在 upload_dir。
- TestUploadHandlerLegacyResponsesUnchanged：/upload 的 400 两种文案 + 「已存文件
  后尾部截断仍 200 上传成功」回归。
